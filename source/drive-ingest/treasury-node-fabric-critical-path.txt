4. CRITICAL PATH WORKSTREAMS
A. Evidence Recovery
Recover actual source, manifests, provider configuration, runtime receipts, logs, node data paths, and chain-specific deployment definitions. Separate claimed implementation from executable assets and operational proof.


B. Canonical Chain Registry
Maintain one authoritative record per chain covering legitimacy, client software, consensus model, node role, adapter coverage, infrastructure requirements, cost, security state, deployment state, and revenue eligibility.


C. Control Plane
Reuse and validate the existing Treasury dashboard, chain registry, custody abstraction, transaction orchestrator, reconciliation, audit logging, event bus, Cybercore policy transitions, and World Monitor telemetry.


D. Representative Node Families
Prepare pilot templates for UTXO, EVM, Cosmos, Solana, XRPL, and Hedera/mirror-node families before broad expansion.


E. Universal Transaction Envelope
Normalize block, transaction, receipt, event, finality, source-node, and verification data into one Treasury event schema.


F. Security Domains
Keep transaction-signing keys, validator keys, withdrawal keys, and infrastructure credentials in separate trust domains. Node containers must not hold general Treasury or withdrawal keys.


G. Acceptance Criteria
A chain is not considered Treasury-housed until the official client is identified, deployed, peered, synchronized, exposed through private RPC, ingested into the common event model, monitored, backed up, and restoration-tested.
